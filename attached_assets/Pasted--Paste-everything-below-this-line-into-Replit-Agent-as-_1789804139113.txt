# 4. DEFINITIONS AND FORMULAS (implement in `app/calc`, with pytest golden tests)
Definitions
- `termination_date` is the LAST working day (inclusive). A worker is ACTIVE on date d if hire_date <= d and (termination_date is null or termination_date >= d).
- roster_hc(d) = count of ACTIVE workers on d, from the `worker` table.
- Headcount for a future month m is always measured on the LAST DAY of m. Actual headcount uses today.
- Vendor headcount on d = sum of headcount of CONFIRMED engagements with start_date <= d <= end_date.
- Fiscal year = 12 months starting at fy_start_month (containing today).

Cost
- Proration: active_days = days in month m on which the item is active (end inclusive, null end = open-ended). factor = active_days / days_in_month. Use integer math, e.g. annual_salary_cents * active_days / (12 * days_in_month), rounded once, ROUND_HALF_UP.
- FTE cost(m) = annual_salary_cents / 12 * factor.
- Vendor cost(m) = headcount * hourly_rate_cents * hours_per_month * factor.
- Round once per line item to whole cents, then sum.
- Golden tests: FTE at 120,000/yr starting the 16th of a 30-day month = 5,000.00. 2 vendors at 50/hr x 160h for the whole month = 16,000.00; active 10 of 30 days = 5,333.33.

Month figures (current month, computed for the full month from current data)
- Cost this month (actual) = sum of FTE cost(month) for workers with any active day in the month + sum of vendor cost(month) for CONFIRMED engagements.
- Plan cost = plan_line.planned_budget_cents for the month. Variance = actual - plan; variance % = variance / plan.
- Committed cost this month = FTE cost from target_start for OPEN positions of APPROVED FTE requests with target_start <= end of month + vendor cost(month) for engagements that are not CONFIRMED, DECLINED or CANCELLED.
- Available budget this month = plan - actual cost - committed cost.
- Unspent from earlier months (INFO ONLY: no action, no carry-forward) = sum over CLOSED cycles in the current fiscal year of (plan_budget - actual_cost) from cycle_summary. Shown to the manager, nothing else.
- YTD actual = closed cycle_summary actual + current month cost. YTD plan likewise.
- Year-end outlook = YTD actual + sum of projected cost for remaining months (Section 7), compared with the sum of the fiscal-year plan. Show two values: with suggestions accepted (primary) and with no action.
- Vendor request total contract value (shown live on the form) = sum of vendor cost(m) over every month from start_date to end_date.

HR decision helpers (informational badges only; HR may always approve)
- Plan-fit for a request = plan_hc[start month] - projected_hc[start month] including this request. Negative means the request takes the team over plan.
- Budget-fit = year-end outlook headroom after adding this request's cost from its start month to fiscal-year end.

# 5. WORKFLOWS AND STATE MACHINES (illegal transitions return 409)
Request: DRAFT -> SUBMITTED -> APPROVED | REJECTED | CHANGES_REQUESTED. CHANGES_REQUESTED -> SUBMITTED (edit and resubmit). DRAFT/SUBMITTED -> CANCELLED (manager). Only HR approves, rejects or requests changes; a note is required for reject and request-changes. Every transition writes approval_event + notification + audit_log.

On APPROVE, in ONE database transaction:
- FTE: create `quantity` OPEN positions and one job_posting (PUBLISHED, unique slug, openings = quantity, description auto-generated from role, grade and team, NO salary).
- VENDOR: create one vendor_engagement (AWAITING_DISPATCH) copying company, headcount, rate, hours, dates.

FTE fulfilment: HR moves an application to HIRED -> dialog (start date, salary prefilled from the request) -> creates a worker (source HIRED_FROM_POSTING, team manager as manager_worker_id) linked to the next OPEN position; that position becomes FILLED. When no OPEN positions remain, the posting becomes CLOSED. HR can pause or close a posting at any time. Cancelling an APPROVED request is HR-only and cancels its open positions and closes its posting (or cancels its vendor engagement).

Vendor fulfilment: HR opens the dispatch queue; the composer is prefilled from a template (company, headcount, role, dates, rate); Send (simulated) -> MESSAGE_SENT. HR marks CONFIRMED or DECLINED. DECLINED notifies the manager, who raises a new request with another company. After CONFIRMED, ACTIVE/ENDED are derived from dates. Vendor HC counts as "actual" only when CONFIRMED and date-active, but counts in projections from approval unless DECLINED or CANCELLED (shown as "unconfirmed").

Roster actions (manager):
- Add person (single form: name, job title, grade, hire date, annual salary, location, optional "link to open position" dropdown; the system proposes a match and the manager confirms in one click). Unlinked additions are flagged UNPLANNED_HIRE.
- Edit (title, grade, salary; effective today, audited; the worker row is updated in place and history lives in the monthly snapshots).
- Record exit (last working day + reason).
- Bulk headcount ("open 10 headcounts for this role at this salary") is ONE request with quantity N, not N requests.

Notifications (in-app): request submitted -> all HR; approved / rejected / changes requested -> manager; posting published -> manager; application received -> HR; vendor message sent, confirmed, declined -> manager; recon flags created -> manager; forecast URGENT suggestion exists -> manager; vendor contract expiring in 30 days -> manager and HR; new month started -> manager.

# 7. FORECAST (deterministic, commitment-based; NO statistical or ML models)
Implement as pure functions in `app/calc/forecast.py`. For each month m from next month to fiscal-year end (k = months ahead of today, L = last day of m):
- projected_fte_hc[m] = roster_hc(L) - round_half_up(actual_fte_hc_today * attrition_pct_monthly * k) + count of OPEN positions of APPROVED FTE requests with target_start <= L. (roster_hc(L) already reflects future-dated hires and exits.)
- projected_vendor_hc[m] = sum of headcount of engagements not DECLINED or CANCELLED that are active on L. Show unconfirmed ones separately.
- gap[m] = plan_hc[m] - projected_hc[m], computed separately for FTE and vendor.

Suggestions (per type, months in order): cum = 0; need = max(0, gap[m]); new = max(0, need - cum); cum += new. If new > 0, suggest {type, quantity = new, start = first day of m, request_by = start - lead_days(type)}. Unit cost is prefilled from the team's average current FTE salary (or the latest vendor hourly rate); if none exists it is blank and required. request_by < today => URGENT. Every suggestion has "Create request", which opens the request form prefilled (source FORECAST_SUGGESTION).

Cost per month: (a) no action = existing workers' prorated cost (respecting future termination dates) + approved OPEN positions from target_start + vendor engagements (non-declined, non-cancelled); (b) with suggestions = (a) + suggested hires at their unit cost from their start month; (c) plan budget. Chart plan vs (a) vs (b), for both HC and cost.

Transparency: every number shows its formula on hover. A "How is this calculated?" panel states plainly: "Commitment-based projection from your roster, approved positions and vendor contracts. It is not a prediction."

What-if panel (live, not saved): hiring delay in months (shifts all OPEN positions and suggestions), attrition % override, hiring freeze from month X (no new suggestions or starts after X), extra hires (type, qty, start month, unit cost). Show delta vs baseline for HC and year-end cost.

Golden tests (pytest):
1. Actual FTE 25; plan 26/27/28; one open position starting mid-month 1. Expect projected 26/26/26, gaps 0/1/2, and suggestions of 1 in month 2 and 1 in month 3 (NOT 1 and 2).
2. A worker with a future termination date lowers projected HC from that month.
3. A FILLED position whose worker starts next month raises projected HC from that month.

P1 extra (only after Phase 7): save up to 3 scenarios, compare side by side, "Promote to requests".
